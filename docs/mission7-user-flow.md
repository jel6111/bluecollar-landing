# 미션 7 사용자 흐름과 화면 명세

2026-11-10 설계안. 아래 경로와 동작은 구현 예정이며 실제 서비스와 연동하지 않는다.

## 기본 흐름

1. 비로그인 사용자가 랜딩의 내 기록 시작하기를 누른다.
2. 로그인 화면에서 계정이 없으면 회원가입으로 이동한다.
3. 이메일·비밀번호·확인을 입력해 가입하고 이메일 확인 안내를 받는다.
4. 유효한 확인 링크를 처리하고 로그인 화면으로 이동한다. 이미 유효 세션이 생긴 경우도 서버 검증 후 허용 내부 경로로 이동한다.
5. 로그인 성공 후 내 기록 목록으로 이동한다. 처음에는 내 기록 없음과 등록 CTA를 표시한다.
6. 등록→내 상세→수정/사진 교체·제거→상세→삭제 확인→내 목록 흐름을 사용한다.
7. 로그아웃하면 랜딩으로 이동하고 보호 경로는 다시 로그인이 필요하다.

## 화면별 입력과 결과

| 화면과 경로 | 입력·사용자 행동 | 성공 결과 | 실패·예외 |
|---|---|---|---|
| 랜딩 / | 서비스 소개, 로그인/내 기록 CTA | 비로그인은 로그인, 로그인 사용자는 내 목록 | 실제 운영 링크/메시징 없음 |
| 회원가입 /signup | 이메일, 비밀번호, 확인, 가입 | 확인 이메일 안내 /auth/check-email | 필수/형식/정책/불일치, 발송/서버 실패 안내, pending |
| 이메일 안내 /auth/check-email | 확인 메일 열기, 로그인으로 이동 | 확인 후 로그인 흐름 | 미수신은 상태/재시도 방법 안내. 자동 반복 발송 금지 |
| 인증 처리 /auth/confirm | Auth 확인 링크 | 서버가 링크를 검증하고 안전한 다음 경로 안내 | 만료/잘못된 링크는 /auth/error, 원문 토큰 노출 없음 |
| 로그인 /login | 이메일, 비밀번호 | 유효 세션과 검증된 next 또는 /records | 계정 유무를 구별하지 않는 오류, 미확인 이메일/발송 제한 등은 필요한 안내 |
| 내 목록 /records?page=1 | 내 기록 열기, 등록, 페이지 선택 | 내 기록과 내 총 개수, 10건 단위 | 첫 기록 없음, 조회 실패 재시도, 세션 만료 안내 |
| 등록 /records/new | 기존 사진/현장/설명/참고 날짜/선택 제목 | 서버 소유자 ID로 저장 후 내 상세 | 검증/업로드/저장 실패 안내, 텍스트·사진 유지. 비밀번호/토큰은 보존하지 않음 |
| 상세 /records/[id] | 읽기, 수정/삭제/목록 | 내 기록과 사진 | 타인 ID와 없는 ID 모두 기록 없음 안내, 존재 여부 누출 방지 |
| 수정 /records/[id]/edit | 기존 값·사진 유지/교체/제거 | 본인 기록만 수정, 상세로 복귀 | 타인/변조 요청 거절, 오래된 화면 거절, 실패 시 기존 자료 보존 |
| 삭제 확인창 | 취소/Esc 또는 확정 | 취소는 상세 유지, 확정은 본인 기록 삭제 후 목록 | DB 실패는 유지, 사진 정리 실패는 본인 큐에 기록 |
| 로그아웃 Server Action | 로그아웃 선택 | 세션 종료 후 / | 처리 실패 시 안내, 성공 전 완료로 표시하지 않음 |

로그인 상태에서 가입/로그인 화면을 방문하면 검증 후 /records로 이동한다. next는 서버에서 허용한 같은 사이트의 /records 및 하위 경로와 유효한 page만 받는다. 외부 URL, //, 역슬래시·중복 인코딩으로 외부 경로를 만드는 값은 거절하고 /records로 보낸다.

## 입력과 세션 처리

- 이메일은 trim하고 형식/길이를 검증한다. 비밀번호는 trim하지 않으며 앱 정책은 12~64자로 계획한다. 새 Auth 제공자의 길이/설정과 일치하는 최종 서버 규칙은 2묶음에서 확인한다. 확인값은 동일해야 한다.
- 계정 존재 여부를 드러내는 상세 오류 대신 사용자가 다음 행동을 할 수 있는 안내를 제공한다. 비밀번호/인증 URL/토큰을 에러/로그/분석으로 보내지 않는다.
- 확인 이메일은 사용자 소유 테스트 주소에만 발송한다. 프로젝트 발송 제한·발신 설정을 확인하기 전 임의 주소/운영 발신 서비스를 사용하지 않는다. 이메일 확인을 임의로 끄지 않는다.
- 원래 기록 경로/page로 돌아갈 수 있도록 하되 사용자 ID를 next나 폼에서 신뢰하지 않는다.
- 모든 Server Action도 세션과 소유권을 재검증한다. 로그인 화면으로 보내는 UI만 접근 제어로 삼지 않는다.
- 로그아웃 후 새 요청/새로고침/뒤로 가기의 보호 데이터가 다시 조회되지 않아야 한다. 이미 사용자가 본 화면·다운로드 파일을 소급 회수할 수 있다고 주장하지 않는다.
- 가입/로그인 처리 중 버튼을 비활성화한다. 실패 시 이메일 등 비민감 입력은 유지하고 비밀번호는 메모리/로그에 장기 보관하지 않는다.

## 핵심 검증 시나리오

계정 A가 사진 기록을 등록한다. A는 새로고침 후 보고 수정/삭제할 수 있다. 계정 B로 로그인하면 A의 목록·개수·상세·사진 URL 발급·변경을 할 수 없다. B의 기록에는 같은 흐름이 동작한다. 로그아웃 상태에서도 두 계정의 보호 데이터에 접근할 수 없다. 주소·요청 payload·SDK 직접 호출을 바꾼 경우까지 검사한다.
