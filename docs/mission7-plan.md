# 미션 7 기능 범위와 구현 계획

작성일 2026-11-10. 사용자 승인 범위는 2묶음 가입·이메일 확인·로그인·로그아웃·세션과 새 과제 Supabase 연결까지다. 인증 코드와 화면은 구현했으며 새 프로젝트 nlvjybohqqkmduqcgzvj를 연결했다. 실제 가입·메일 확인·로그인은 확인했고 새로고침 유지·로그아웃 후 접근 제한도 사용자가 수동 확인했다. 자동 계정 검사는 건너뛰었다. 3묶음 CRUD/RLS와 4묶음 배포는 아직 진행하지 않는다.

## 선택 이유와 완료 목표

미션 6은 공용 가상 기록을 누구나 읽고 변경하는 데모였다. 이번에는 **회원별로 자기 작업기록과 사진만 관리**하도록 소유권을 추가한다. 대상은 사진과 짧은 설명으로 작업을 기록하는 현장 작업자이며 과제에서는 사용자가 관리하는 테스트 계정과 가상 기록으로 검증한다. 실제 운영 전환·사용자 성과는 주장하지 않는다.

## 최소 범위

| 기능 | 이번 범위 | 완료 기준 |
|---|---|---|
| 회원가입 | 이메일·비밀번호·비밀번호 확인 | 검증 후 가입 처리, 이메일 확인 대기 안내 |
| 이메일 확인 | 새 과제 Auth의 확인 링크 | 유효 링크는 처리 후 로그인 흐름, 만료/오류 링크는 안내 |
| 로그인·로그아웃 | 이메일·비밀번호, 서버 세션 | 로그인 유지/종료, 검증된 내부 복귀 경로 |
| 보호된 화면 | /records와 하위 경로 | 비로그인은 로그인으로 안내, 서버도 재검증 |
| 내 기록 CRUD | 기존 등록·목록·상세·수정·삭제 | 소유자 연결, 목록 수/페이지도 본인 범위 |
| 내 사진 | 기존 1장, 유지·교체·제거 | 사진 URL 발급·다운로드·업로드·삭제에서 동일한 소유권 경계 |
| 상태 안내 | pending, 검증 오류, 빈 상태, 만료 | 사용자가 현재 상태와 다음 행동을 이해할 수 있음 |

이번 최소 범위에 결제·AI·카카오/Google OAuth·프로필 편집·회원 탈퇴·비밀번호 재설정·팀 공유·관리자 화면·운영 데이터 이관을 포함하지 않는다. 비밀번호 재설정과 소셜 로그인은 추후 Auth 모듈에 확장할 수 있다.

## 기술 선택과 이유

기존 Next.js App Router와 Supabase DB/Storage에 Supabase Auth를 연결한다. 하나의 사용자 ID로 기록과 사진의 소유권을 연결하고 별도 인증 서버를 만들지 않는 방향이다. Supabase의 쿠키 기반 SSR 클라이언트를 검토하고, 서버에서 사용자 세션/토큰을 검증한다. 화면 제한과 DB/Storage RLS를 함께 적용한다.

장점은 기존 기술 기반과 사용자 ID/정책을 공유하는 점이다. 제한은 이메일 확인·발송 설정과 세션 갱신, 파일 권한/보상 정리까지 검증해야 한다는 점이다. 일반 CRUD는 로그인 사용자 클라이언트를 쓰며 기존 관리자 키 클라이언트를 기본값으로 두지 않는다.

공식 근거: [Next.js 서버 인증](https://supabase.com/docs/guides/auth/server-side/nextjs), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage 접근 제어](https://supabase.com/docs/guides/storage/security/access-control). 2묶음 코드는 Next.js 16.4.6과 @supabase/ssr 0.12.7을 사용한다. 새 Auth의 이메일 설정과 실제 메일 수신은 프로젝트 연결 후 확인해야 한다.

## 기존 MVP에서 유지할 동작

사진→현장 이름→짧은 설명, 선택 제목 자동 보충, 참고 날짜/work_date와 등록일/created_at 구분, 10건 페이지네이션, 중복 제출 방지, updated_at 기반 충돌 거절, 사진 실제 디코딩·EXIF 제거·3 MiB 제한, 실패한 입력 유지·사진 정리 보상, 키보드 사용과 모바일 레이아웃을 보존한다. 이 동작은 새 과제 자원에서 다시 검증한다.
